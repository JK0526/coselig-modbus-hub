## S402 setup and entity lifecycle

- [ ] After gateway validation, setup offers S402 configuration without requiring or starting a Modbus scan.
- [ ] S402-only Gateway can complete setup with polling set to 0 and no Modbus devices.
- [ ] One configured S402 creates exactly four EventEntity instances for DI1–DI4 under one `Coselig S402 #<id>` device.
- [ ] Entities report `PRESS_END` for a single click; no press-down, release, double-click, or long-press events are emitted.
- [ ] Unknown but valid S402 IDs appear as unconfigured Monitor events and do not trigger a configured entity.
- [ ] Invalid CRC, invalid DI values, and truncated candidate frames do not trigger an event or alter Modbus request / CRC statistics.
- [ ] Repeated rapid clicks on the same DI are all retained as distinct EVENT rows and events.
- [ ] Reload and unload remove old listeners; re-setup does not duplicate events or entities.
- [ ] Gateway disconnect makes S402 EventEntity instances unavailable; reconnect restores availability without reloading the integration.

## Bus coexistence and address reservation

- [ ] With S402 configured, ordinary Modbus Slave #1 cannot be added; the UI explains the reserved-address conflict.
- [ ] If ordinary Modbus Slave #1 already exists, adding S402 is rejected without changing the existing entry or registry identity.
- [ ] Scanner may report Slave #1 while S402 is configured, but the result is visibly marked as conflicting and cannot be added.
- [ ] S402 #51 and Modbus Slave #51 coexist because S402 IDs and Modbus Slave addresses use separate namespaces.
- [ ] No ACK, echo, read-back, or other Modbus request is sent in response to an S402 event.

## Continuous RX under Poll and Control

- [ ] Verify `TX → EVENT → RX → OK`: the poll/control response is still matched to its original request and the event is emitted independently.
- [ ] Inject multiple events while a request is pending; events do not complete the pending request or extend its original timeout.
- [ ] Polling continues at the configured interval with S402 events present; event volume does not grow the control queue or create poll backlog.
- [ ] With Polling=0, Continuous RX still receives and emits S402 events.
- [ ] Gateway EOF/reset causes Coordinator-managed reconnect; intentional unload/reload does not create a false connection-loss/reconnect cycle.
- [ ] P404 / P210 lights and R410 switches retain their existing control, polling, and availability behavior on the same supported bus topology.

## Monitor and soak test

- [ ] Each S402 frame appears as a standalone `EVENT` row with timestamp, raw HEX, S402 ID, DI, single-click type, and configured/unconfigured status.
- [ ] EVENT filter includes and excludes event rows as expected; EVENT rows do not merge into adjacent TX/RX transactions.
- [ ] S402 events do not increment successful, failed, timeout, CRC-error, or reconnect Modbus request counters.
- [ ] Run at least a 24-hour soak test (48 hours recommended) with normal Poll / Control use and repeated S402 clicks.
- [ ] Record request counters, reconnects, queue peak, event delivery, task/socket health, and any log errors at start and end.
- [ ] Record any missed, duplicate, delayed, or misrouted event and attach relevant masked diagnostics/log evidence.

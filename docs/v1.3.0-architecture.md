# Coselig Modbus Hub v1.3.0 架構

本版為 architecture + device support minor release。目標是集中產品知識，加入 R410 Relay-only 支援，保留 v1.2.1 的 dimmer 行為與 HA registry identity。

## DeviceProfile

`models.py` 保存 Device 設定與純 brightness／CCT conversion；`profiles.py` 的 `PROFILES[Model]` 是各 model 的 family、group fields、supported platforms、poll block、outputs、decoder 與 command codec 來源。

| Profile | Family | Runtime poll | Outputs／command |
| --- | --- | --- | --- |
| Coselig P404 | DIMMER | FC03 start 0x082A count 4 | CH1～4 或 Group A/B CCT；FC06 |
| Coselig P210 | DIMMER | FC03 start 0x082A count 2 | CH1/2 或 Group A CCT；FC06 |
| Coselig R410 | RELAY | FC01 start 0 count 4 | Relay 1～4；FC05 |

`PollSpec(function,start,count)` 建立 request，並將 response decode 至 address-keyed 狀態。`OutputSpec` 定義 stable key、預設顯示名稱、address tuple 與 HA platform。`Device.profile` 以一處 lookup 取得能力；Config Flow 依 `group_fields` 產生表單，Coordinator 不含 model if-chain。

`DeviceState` 具備 `holding_registers`、`input_registers`、`coils`、`discrete_inputs` 四種 dictionary，加上 availability、failure counter 與 poll timestamp。每輪先在暫時 `ModbusData` decode 所有 blocks，成功才提交 state，避免半完成狀態。Light 以 register address 取值，Switch 以 coil address 取值。

Dimmer 的 `0x05xx` 寫入與讀取低 byte／0～100 驗證集中在 Profile。`0 → 0x0500`、`49 → 0x0531`、`100 → 0x0564` 保持不變；brightness、CCT、最低亮度 conversion 未修改。

## Generic RTU protocol

`protocol.py` 只處理 Modbus RTU：FC01 coils、FC02 discrete inputs、FC03 holding registers、FC04 input registers、FC05 single coil、FC06 single UINT16 register。Slave 範圍維持 1～247，address/value 為 UINT16，read count 依 Modbus 範圍（bits 1～2000、registers 1～125），讀取範圍不得越過 0xFFFF。

FC01～04 依 byte_count 讀取 payload；FC05/06 為 8 bytes echo；exception 為 5 bytes。保留 fragmented/coalesced stream、CRC、slave、function、expected byte_count、完整 echo 驗證。FC05 ON=FF00，OFF=0000。沒有 FC0F/FC10。

Transport、priority queue、TraceBuffer 與 Monitor 未變更。新 function 經相同 submit/receive/validate 路徑，自動進入既有 TX/RX/status/latency trace。timeout、壞封包或 TCP 錯誤沿用 disconnect 清理，exception 不被誤認為 Gateway hard failure。

## Scanner pipeline

1. 使用者先選 1～247 範圍，再按開始搜尋；UX 與上次範圍保存不變。
2. Common discovery：FC03 start 0 count 1（40001）。合法 normal response 才列為 found，不比較 register 內容與 Slave ID。
3. Family identification：先 FC03 0x082A count 2；normal success → DIMMER、candidates P404/P210。成功後不執行 Relay probe，也不嘗試 count4 辨識 P404。
4. Dimmer probe 未匹配時，以 FC02 start 0 count 4 辨識 Relay；normal success → RELAY、recommended R410。兩者皆未匹配 → UNKNOWN、全部 model 候選。
5. Model confirmation：使用者確認型號；R410 跳過 groups，dimmer 依 Profile 設定 single/CCT。

`ScanResult` 是 transient dataclass，不保存 probe evidence、family 或 candidates。Normal、exception、timeout、CRC 與 TCP error 分流：不支援 function 只代表 probe 未匹配，以 DEBUG 記錄，不修改 runtime device failures/availability。TCP hard error 仍傳回 Hub 處理 Gateway offline。

掃描持有 Coordinator round lock 與 Transport exclusive gate；正常 polling/control 不穿插。成功、失敗或取消都釋放鎖並喚醒既有 scheduler；非零 interval 立即同步，Poll=0 繼續等待。既有設備保留 model/groups，偵測結果只提供新設備的建議。Missing 不自動刪除。

## R410 Relay implementation

`switch.py` 只建立四個 HA `SwitchEntity`，不載入 `binary_sensor`。每個 Relay 具獨立 Child Device，名稱為 `R410 #70 · Relay 1` 等；`_attr_has_entity_name=True`、`_attr_name=None`。

四個 wire coil address 為 0、1、2、3。每顆 R410 每輪只用一筆 FC01 count4，bit0～3 對應 Relay 1～4；沒有 runtime FC02/DI polling。控制各送一筆 FC05，先 optimistic 更新 HA，再等同一 queue 的 command；不做 read-back、write retry/replay，也不在 failure 時立即 rollback，下一輪 poll 才校正。舊 poll 不覆蓋較新的 optimistic 操作。

維持一筆 in flight、control > poll、capacity32、pending latest-wins、不同 Relay 不合併。failure threshold3、next success recovery、hard gateway failure all unavailable、Poll=0、reconnect backoff 都沿用原設計。Poll=0 的 relay control/scan/monitor 仍可用，恢復非零 interval 立即 full sync。

R410 不提供 DI entities/config、Scene、Toggle/Momentary registers、linkage 或 power-on mode。HA 標準 SwitchEntity 基類可能提供一般 toggle service，實作只會轉成正常 ON/OFF FC05，沒有使用硬體 Toggle register。

## Backward compatibility 與 Area

Config Entry schema 保持 2.1。P404/P210 serialization 相容；缺少 P210 group_a 仍預設 single。R410 只增加 `{"slave":70,"model":"r410"}`，不保存 groups。

Parent identifier：`{entry_id}_slave_{slave}`。Child identifier／entity unique_id：沿用 `_ch1`～`_ch4`、`_group_a`／`_group_b`；Relay 新增 `_relay1`～`_relay4`。沿用原生 `ChildDeviceInfo` 與真實 Parent ID，無 via_device、Area mapping 或名稱 migration table。

同 unique_id 由 HA 原地更新；不刪除既有 entity registry entry，因此 entity_id、registry ID、automation target、custom entity/device names、Area、Parent/Child IDs 都保留。只有使用者明確移除／切換 mode 的過期 outputs 才走既有 prune lifecycle。prune 先刪過期 Child，再刪 Parent，避免 HA parent cascade 後二次刪除 Child。

## 驗證與規格來源

測試使用固定 HA 2026.10.1／Python 3.14.7、真實 HA registry 與 loopback RTU Gateway。涵蓋 generic functions、exception/CRC/fragment/coalesce、family identification、混合設備流量、optimistic/queue/failure/recovery/Poll=0、Area/name/identity migration。

- [官方 Modbus Application Protocol V1.1b3](https://www.modbus.org/file/secure/modbusprotocolspecification.pdf)：通用 functions、quantity、encoding、echo。
- [官方 HA SwitchEntity](https://developers.home-assistant.io/docs/core/entity/switch/) 與 [Device Registry](https://developers.home-assistant.io/docs/device_registry_index/)：native switch 與 child registry。
- Device register map 與 dimmer 0x05 語意依本次使用者規格。工作區／附件未提供產品手冊，故沒有宣稱已直接核對手冊或完成 R410 實機驗收。
